# V1: what's done, what's left

V1 goal: a Windows PC, a Mac, an Android phone and a Samsung tablet find, pair
with and send files, text, links, clipboard and media to each other on the same
Wi‑Fi or a phone hotspot, with no internet or cloud needed.

Inventory taken 2026-11-05 on `audit-2026-10-26` at `3e4a855`. Security work
(encryption, forward secrecy, revocation) is finished for V1 and kept as is;
further hardening waits until after V1 ([encryption.md](encryption.md), "What's left").

**Status:**

- **Tested:** built, with automated tests (unit, multi-app integration, browser end-to-end, CI on every platform).
- **Built:** built, but some parts lack an automated test.
- **Partial:** part of the feature is missing.
- **Missing:** not built.
- **Platform limit:** the OS or browser doesn't allow it.

**Real device** is what a person checked on hardware, from [audit-2026-10-26.md](audit-2026-10-26.md). "Not yet" means no evidence; it doesn't mean it failed.

## Platform limits (not planned)

- **iPhone / iPad app:** browser only.
- **A web page reading the clipboard in the background:** browsers don't allow it.
- **Accept / Decline inside a browser notification on plain `http://`:** needs a service worker, which needs a secure context.

## V1-QA: real-user workflows (2026-11-06)

Run against real app processes (three local apps, the page driven in a browser) and in integration tests with simulated clocks.
**Automated** means a test that runs in CI; **walkthrough** means checked by hand in the real UI on this Mac. Neither is a real-device check.

| Workflow | How it was checked | Found and fixed | Evidence |
|---|---|---|---|
| Sender's window closed before the transfer started | Walkthrough (4 min wait) + automated | The sender kept it "accepted" for ever and never recorded it. Now: **Failed — the window sending it closed. Choose the files again**, the receiver is told, and both sides record it | `test_stalls.py`; walkthrough: Mac "Failed" with that reason, tablet "Studio Mac didn't start sending." |

| App killed (`kill -9`, power loss) | Walkthrough + automated | Can't be caught by the killed app. The other side ends it (sender: "Couldn't reach"; receiver: "stopped sending" after 10 min); `.part` files are deleted on the next start | `test_disconnected_partway`; walkthrough: killed PC → "Couldn't reach Office PC." |

**On real hardware (2026-11-07, run by a script, no person at the screens):** Mac, a Windows 11 laptop (CLI build) and an Android phone on home Wi‑Fi. Transfers in three directions, groups, decline, expiry, retry, notification Accept, pairing, partial retry, 1 GB, and apps killed or stopped mid-transfer all behaved as above. One defect found and fixed: stopping the command-line app with SIGTERM (`kill`, `systemctl stop`, `docker stop`) skipped the shutdown, so receivers waited 10 minutes; a dropped sender is now named (*Lost connection to …*). Repeated test runs that night also caught quitting hanging for ever about once in 16 stops (Ctrl+C or SIGTERM interrupted the web server while it held a lock); fixed with a test. Details and what still needs a person: [device-testing.md](device-testing.md#run-on-real-hardware-by-automation-2026-11-07).

**Known gaps (not fixed, by design or for later):**

- Files chosen in a page live only in that page. After the window closes, a retry needs the files chosen again, and the reason says so. A browser can't reopen files by itself.
- A send killed with its app (`kill -9`) isn't in the sender's own history, because nothing on that machine ran to write it.
- A retry that skips files already there reports its speed as if they had been sent (39 MB/s on a phone for 3 photos).
